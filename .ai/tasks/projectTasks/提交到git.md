# 提交到 git

对当前仓库完成 git 初始化（如需要）与本地提交，提交说明须带版本号，并展示最近提交记录。

## 目标

1. 若仓库尚未 `git init`，先完成本地初始化。
2. 将当前变更完成本地提交；说明须写清提交了什么，并带上本次版本号。
3. 提交成功后向用户展示最近 5 次提交。

## 版本号规则

格式：`vX.Y.Z`（如 `v0.0.1`）。

1. **首次带版本提交**：仓库历史中尚无 `vX.Y.Z`（含尚无任何 commit）时，本次固定为 **`v0.0.1`**。
2. **其后每次提交**：读取最近一次带版本号的 commit，按**本次变更体量**递增（只加对应位，该位以下归零）：
   - **增加功能模块**（新模块/新目录级能力、大块子系统）→ **X+1**，Y、Z 归零（如 `v0.2.3` → `v1.0.0`）。
   - **增加小功能**（既有模块上的新能力、较完整的小特性）→ **Y+1**，Z 归零（如 `v0.2.3` → `v0.3.0`）。
   - **优化、修小 bug、小需求**（文案/结构微调、缺陷修复、轻微改进）→ **Z+1**（如 `v0.2.3` → `v0.2.4`）。
3. 一次提交只选一档体量：取变更中**最高**那档（既有修 bug 又有新模块 → 按功能模块加 1）。
4. 版本号写入提交说明开头，推荐格式：
   ```text
   vX.Y.Z <写清提交了什么>
   ```

## 执行步骤

1. 检查当前目录是否为 git 仓库（例如 `git rev-parse --is-inside-work-tree`）。若不是，执行 `git init`。
2. 并行查看：`git status`、`git diff`（含已暂存与未暂存）、`git log -5`（若尚无提交可跳过 log）。
3. 从 `git log` 解析最近一次 `vX.Y.Z`；若无，则本次版本为 `v0.0.1`。若有，按上方规则根据 diff/status 判定体量并计算新版本。
4. 根据变更自动起草提交说明（写清提交了什么），并加上版本号前缀；用户若已给出备注，保留其含义并确保以 `vX.Y.Z` 开头（用户已带正确版本则沿用，未带则补上本次算出的版本）。
5. 暂存相关变更并直接提交，不要向用户确认：
   - 默认不提交疑似密钥/凭证文件（如 `.env`、`credentials.json` 等）；发现时跳过并在结果中说明。
   - 用 HEREDOC 传递提交说明，例如：
   ```bash
   git add <相关文件>
   git commit -m "$(cat <<'EOF'
   vX.Y.Z <提交说明：写清提交了什么>

   EOF
   )"
   ```
6. 提交完成后执行 `git log -5 --oneline`（或等价命令），把最近 5 次提交展示给用户；并再跑一次 `git status` 确认工作区状态。回复中注明本次版本号与所选用的体量档（模块 / 小功能 / 优化修补）。

## 产出

- 一次成功的本地 commit（说明含 `vX.Y.Z`），或说明无需提交的原因。
- 最近 5 次提交列表（不足 5 次则展示全部）。
- 本次版本号与递增依据（一句话即可）。

## 约束

- 直接执行，不要询问用户确认备注、版本号或是否提交。
- 只做本地操作：初始化（如需）+ 暂存 + 提交；除非用户明确要求，否则不 `push`、不打 git tag、不改 `git config`、不做 force/rebase 等破坏性操作。
- 不要使用 `--no-verify` 等方式跳过 hooks，除非用户明确要求。
- 若没有可提交变更，说明现状并展示最近提交，不要创建空提交，也不要空递增版本号。
