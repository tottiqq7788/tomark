# 新增功能审查

对当前项目代码（尤其是最新提交的变更及相关模块）做代码审查；发现明确必须修复的问题时直接修复并补测。

## 目标

1. 只读审查最新变更与相关模块，找出 bug、结构、死代码与测试缺口等问题。
2. 按「必须修复 / 建议优化 / 暂不处理」分类结论。
3. 对必须修复项直接改代码并补充必要测试，再跑相关验证。

## 输入

- 审查范围默认：最新一次（或用户指定的）git 提交所改文件及其相关模块；若工作区有未提交变更，一并纳入。
- 项目约定：`agent.md`（含目录落盘规则）、现有测试与诊断命令。
- 范围不清时以「最新提交 + 未提交变更」为准，不必反复确认。

## 执行步骤

1. 确定变更集：`git log -1 --stat`、`git show` / `git diff`（含工作区），列出待审文件与关联模块（遵守开发目录，不在根目录乱翻堆砌文件）。
2. **先只读审查**，重点检查：
   - 明显 bug、回归风险、边界条件遗漏、数据迁移问题。
   - 大文件、超长函数、职责混杂、组件化/模块化较差。
   - 死代码、未使用代码、重复逻辑、过期兼容路径、可疑测试/示例遗留。
   - 测试覆盖是否足够，是否需要补充或调整测试。
3. **可并行**：用便宜模型 / subagent 分方向检查（互不阻塞），例如：
   - 大文件与复杂度。
   - 组件化与模块边界。
   - 死代码、重复逻辑与过期兼容路径。
   主代理汇总各方向结果，去重并定级。
4. 将结论分为三类：
   - **必须修复**：会导致错误、数据丢失、回归、安全风险或明显测试缺口。
   - **建议优化**：结构、可维护性、组件拆分、重复逻辑等非阻塞问题。
   - **暂不处理**：需产品/历史兼容确认，或风险高于收益。
5. 对 **必须修复**：直接改代码并补充必要测试；改动落在既有开发目录（如 `src/`、`src-tauri/`、`tests/`）；不要为风格或大重构扩大范围。
6. 修复后运行相关测试与诊断；无法运行的测试须说明原因。
7. 最终回复必须包含：
   - 修复了哪些问题。
   - 仍建议后续优化但本次未处理的事项。
   - 已运行的验证命令和结果。

## 产出

- 分类审查结论（必须修复 / 建议优化 / 暂不处理）。
- 必须修复项对应的代码与测试改动（若有）。
- 验证命令与结果说明。
- **不**向 `plan/` 写入审查文档（除非用户另行要求归档）。

## 约束

- 先只读、再定级、再动手；未定为「必须修复」的不要顺手大改。
- 必须修复才改代码；建议优化与暂不处理只记录在回复中。
- 修复范围最小化，禁止借审查做无关重构或根目录堆砌文件。
- 需求清晰时直接审查并修复必须项，不要反复确认是否开工。
- 遵守 `agent.md` 落盘规则；依赖相关改动优先落在 `deps/` 约定位置。
