# 新功能开发规划

按用户需求与当前技术栈，在 Cursor（或其他 IDE）的 Plan 模式中做详细开发规划；用户确认后直接落地实现。本任务不向 `plan/` 写入任何文档。

## 目标

1. 在 Plan 模式中给出可执行的新功能开发规划（贴合当前技术栈，栈不固定）。
2. 涉及界面时，在规划内容里用文字线框图说明布局。
3. 用户确认后按**已初始化的开发目录**落地实现（不在根目录堆代码）。

## 输入

- 用户对新功能的需求描述。
- 当前技术栈与约定：从 `agent.md`、`readme.md`、依赖与目录结构推断。
- 需求足以开始规划时直接进入 Plan；缺到无法判断「要开发什么」时再询问。

## 执行步骤

1. **进入 Plan 模式**：若当前不是 Plan（计划）模式，先切换到 Plan 模式，再做规划。
2. 读取实现上下文：`agent.md`（含目录职责与落盘规则）、`readme.md`、现有开发目录（如 `src/`、`src-tauri/`、`tests/`）内源码；需要时只读参考 `plan/prd` 归档，**不要**新建或改写 `plan/` 下文件。
3. 在 Plan 模式中输出详细开发规划（给用户审阅，不是落盘到 `plan/`），至少包括：
   - 要改/要建的**模块路径**（必须落在已有开发目录内，写清如 `src/...`、`src-tauri/...`、`tests/...`）
   - 功能点与实现步骤（可执行、可验收）
   - 关键流程与边界情况
   - 风险与不做的范围
   - 若现有顶层开发目录不够：在规划中列出建议新增的文件夹名，并标明**须先征得用户同意**才能创建
4. **若存在界面**：在规划正文中附**文字线框图**（仅用于 Plan 对话展示），示意：
   ```text
   ________________________
   |        示例标题        |
   |______________________|
   | 侧栏 |     主内容区     |
   |      |                |
   |______|________________|
   ```
5. **等待用户确认**；用户表示没问题 / 同意执行后：
   - 切回 Agent（或可写代码的执行模式）
   - 按规划在对应开发目录内实现
   - 若规划依赖新增顶层文件夹：仅在用户已明确同意「可以增加 XXX」后创建；顶层开发相关文件夹总数仍应保持在 **2–5 个**（不含 `plan`、`.ai`、`.git`）
6. 实现完成后简要说明改动路径与如何验收；**PRD 归档不在本任务内**（先开发、再归档，需要时另执行「prd归档」）。

## 产出

- Plan 模式中的详细开发规划（含必要的文字线框图）。
- 用户确认后的代码/配置等实现改动（位于开发目录内）。
- **无** `plan/` 目录下的新文件或更新。
- **无**在仓库根目录新增的业务/源码堆砌文件。

## 约束

- 「规划」仅指 IDE 的 **Plan 模式规划**，不是往 `plan/` 写产品文档。
- **禁止**因本任务在 `plan/prd`、`plan/misc` 创建或更新任何文件。
- **禁止**在项目根目录直接创建/堆砌开发源码文件；一律放入初始化后的目录（如 `src`、`src-tauri`、`tests`）。
- 现有开发目录不足时：**询问用户是否可以增加「XXX」文件夹**，未同意不得擅自新增顶层开发目录。
- 根目录开发相关文件夹保持 **2–5 个**；不要为新功能擅自摊开更多顶层目录。
- 不在 Plan 模式时必须先切换再规划；未获用户确认前不要大规模改代码。
- 用户确认后直接执行实现，不要反复确认、不要先写 `plan/` 文档再开发。
- 技术栈以当前仓库为准；信息不足时在 Plan 里写清假设，不要虚构已有实现。
- 不把密钥、内网地址、账号密码写进对话规划或代码。
