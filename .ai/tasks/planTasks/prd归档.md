# prd 归档

根据当前已开发内容与最新 git 版本号，回溯整理并归档一份 PRD（先开发，再落地文档）。

## 目标

1. 以仓库**当前实现**与约定为准，归纳已落地的产品能力与边界。
2. 结合最新 git 版本号生成归档 PRD，写入 `plan/prd/`。
3. 在回复中给出归档摘要与文件路径。

## 输入

- 当前代码与结构：顶层模块目录、关键实现、测试与配置中能反映的能力。
- 项目约定：`agent.md`、`readme.md`，以及已有 `plan/prd/`、`plan/misc/`（作对照，避免无意义重复）。
- 最新版本号：从 `git log` 最近一次带 `vX.Y.Z` 的提交解析；若历史无版本号，在文档与文件名中标明 `v0.0.0`（未版本化）或先提示用户执行「提交到git」后再归档——仅当完全无法判断项目状态时才询问。

## 文件命名

路径与文件名固定为：

```text
plan/prd/{项目名}{版本号}{YYYYMMDD}.md
```

- **项目名**：优先取仓库根目录名；若与 `agent.md` / `readme.md` 公开名明显不一致，以公开项目名为准（短英文，无空格）。
- **版本号**：最新 git 提交中的 `vX.Y.Z`（含前缀 `v`），例如 `v0.0.1`。
- **YYYYMMDD**：执行归档当天的本地日期。
- 示例：项目 `tomark`、版本 `v0.0.1`、日期 `20260806` → `plan/prd/tomarkv0.0.120260806.md`。
- 同名已存在则覆盖更新为本次归档内容（或在文首注明覆盖原因）；不要另起一堆近义文件名。

## 执行步骤

1. 确认/创建 `plan/prd/`、`plan/misc/`（不存在则建；不挪动 `.ai/`）。
2. 读取最新开发内容与约定：
   - `git log -5 --oneline`、`git status -sb`（了解版本与是否有未提交改动；有未提交改动时在 PRD 中注明“含工作区未提交能力”或建议先提交再归档，默认仍按当前工作区+HEAD 如实描述已存在能力）。
   - `agent.md`、`readme.md`、主要源码/目录职责、已有 plan 文档。
3. 解析**项目名**、**最新版本号**、**当日 YYYYMMDD**，得到目标路径 `plan/prd/{项目名}{版本号}{YYYYMMDD}.md`。
4. 撰写归档 PRD（反映「已经做成什么样」，不是愿景清单），至少覆盖：
   - 文档元信息：项目名、版本号、归档日期、对应 git 提交（短 hash + 说明）
   - 产品定位（一句话，与实现一致）
   - 已实现能力（按模块/用户可感知功能列举）
   - 明确未做 / 非目标（实现中尚不存在或约定不做的）
   - 技术栈与目录映射（与当前仓库一致）
   - 已知限制或后续可迭代点（精炼，不空谈路线图）
5. 写入上述路径；过程性摘录如需保留可放 `plan/misc/`，主归档只留 PRD。
6. 回复摘要 + 完整文件路径 + 所用版本号；直接完成，不要再确认是否保存。

## 产出

- `plan/prd/{项目名}{版本号}{YYYYMMDD}.md` 归档 PRD 一份。
- 回复中的归档摘要。

## 约束

- 这是**开发后归档**：以代码与现有约定为准回溯成 PRD，不要按未实现想法写成“计划有”。
- 能直接归档则直接写文件；仅当项目名/版本完全无法确定时再询问。
- 不在此任务中改业务代码、不做版本号递增、不替用户 `git commit` / `push`（提交用「提交到git」任务）。
- 不把密钥、内网地址、账号密码写入 `plan/` 文档。
- 文风具体可核对，避免空洞愿景和过细到函数级的设计说明书。
